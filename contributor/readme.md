# README 规约

本文件规定 BORUIX 各仓库 README 的写法和内容边界。目的是让 README 的形态**一次做对**，而不是
反复返工。

## 两个文件

- `README.md` —— 中文，短
- `README.en.md` —— 英文

两个文件在**顶部互相链接**（`[English](README.en.md)` / `[简体中文](README.md)`）。

> 本规约文件自身同样不使用表格，以免规则与示例不一致。

## 内容判据

每写一节，逐条自问：

1. **公众需要读吗？**——是则留在 README
2. **长期维护者需要读吗？**——是则写进 `wiki/contributor/{仓库名}.md`
3. **初次的外部维护者需要读吗？**——是则写进 `wiki/contributor/{仓库名}.md`

三条都不满足的内容**不写**。

这条判据的关键在**后两条的落点是 wiki，不是 README**。设计论证、"这一步很重要"式的说明、与
历史设计文档的对话，都属于维护者内容。

### 典型误判

**把维护者内容翻译成自然语言后留在 README。** 去掉 `ADR-041` 这样的内部代号，写成"早期设计中
曾有一项禁令"，读起来像面向公众了，**其实还是在跟内部设计文档对话**——读者根本不知道那个"早期
设计"是什么。**代号不是问题，定位才是。**

## 结构

```
# 仓库名

一句话：它是什么、解决什么问题。

[English](README.en.md)

## 功能 / 覆盖范围 / 测什么
## 使用
## 已知限制（可选）
## 构建
## 仓库布局（可选）
## 相关项目
## 许可
```

小节按仓库性质取用，不必全有。库和驱动通常写"功能"或"覆盖范围"，验收程序写"测什么"，
守护进程写"它做什么"。

## 写法

### 不用表格

README 正文**不使用表格**。要列东西就用 `-` 列表。

理由：项目参照的 README（Redox 各子仓库）**无一使用表格**，它们用散文加列表。表格把句子切成
碎片，读起来像配置项说明，不像一个程序。

### 列表只列必要项

`-` 列表是允许的，但**不要逐项罗列显而易见的东西**。

反例：行编辑库的功能列表写"输入、退格、删除"——这是行编辑器理所当然要做的事，等于没说。

正例：只说这个库**特有**的部分，比如"回显抑制：供口令输入使用"。

### 仓库布局用列表，不画树，不求全

用 `-` 列表，**只列目录和关键文件**，同类文件合并成一行。

反例：把 25 个源文件画成树形图，每个文件一行注释。

正例：

```
- `src/lib.rs` —— 模块导出
- `src/io.rs`、`mem.rs`、`process.rs` —— 各领域接口
```

### 第一句就说清楚它是什么

参考项目的开头是一句直述：`This repository contains the core UNIX utilities for Redox OS.`、
`Network Utilities for Redox`。

不要用"本节介绍……"这类空转的开场。

### 只写事实，不写论证

可以写"最多 3 次"、"不区分用户不存在与口令错误"。

不要写"这样设计是因为……"、"这一步很重要"。理由属于 wiki。

## 内部代号一律不出现

ADR 编号、批次号、阶段号、里程碑编号、内核内部函数名与结构体名，**都不进 README**。

但以下**保留**，因为它们对读者有直接用处：

- 真实的系统调用名、标准库函数名
- 真实路径（`/programs/*.elf`、`/scratch/*`、`/devices/*`）
- 程序真实打印的输出字符串
- 通用技术名词（POSIX、PAM、MMIO、DMA）

## 长度

参照项目的实测范围**很宽**，从 28 字符到 5683 字符：

- `redox-fatfs` 28、`liborbital` 197、`extrautils` 218、`netutils` 245
- `coreutils` 728、`redoxfs` 1860、`orbclient` 2401
- `relibc` 5683、`pkgar` 4584

长的那些并非注水——`relibc` 与 `pkgar` 包含**格式规范与完整构建步骤**，内容本身就有那么多。

所以**不设字数上限**。判断标准只有一条：**按内容判据过一遍，该留的留、该移 wiki 的移走**。
移完之后剩下多少就是多少。

实践中，纯程序仓库精简后通常落在 **800–1500 字符**；库和带规范的仓库会更长。

## 许可文件

每仓库一份 MIT `LICENSE`，与 [`audiod`](https://github.com/BRX-Boruix/audiod) 的逐字节一致，
内容为 `Copyright (c) 2026 Yang Borui`。

例外：上游 fork 保留其原许可（`brxLimine` 为 BSD-2-Clause）；`gcc-on-boruix` 跟随上游 GPL，
不另加。

## 改完必做

1. 核对源码——**README 里的每个数字和行为都不能来自旧 README 的自述**。旧 README 常有与实现
   脱节的陈述（例如某模块头声明停留在早期阶段，而代码已推进数轮）。
2. 更新 `README_STATUS.md`（仓库根目录，仅内部），**与改动同一轮完成**。
3. 提交并推送，核对本地与远端哈希一致。

## 参照项目

`其他项目/redox-os-repos/` 下的 README 是本规约的来源：

- `extrautils`、`netutils`、`liborbital` —— 一句话加徽章，197–245 字符
- `coreutils` —— 散文加"Currently included:"列表，728 字符
- `redoxfs` —— 安装与使用步骤，1860 字符
- `relibc` —— 库的完整形态：介绍、职责列表、仓库布局、构建、测试，5683 字符
- `redox-subrepos/kernel` —— 内核仓库，3275 字符
